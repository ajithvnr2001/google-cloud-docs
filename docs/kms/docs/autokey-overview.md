#  Autokey overview Stay organized with collections  Save and categorize content based on your preferences. 

Cloud KMS Autokey simplifies creating and using [customer-managed encryption keys (CMEKs)](https://docs.cloud.google.com/kms/docs/cmek) by automating provisioning and assignment. With Autokey, key rings and keys are generated on-demand. Service accounts that use the keys to encrypt and decrypt resources are created and granted Identity and Access Management (IAM) roles when needed. Cloud KMS administrators retain full control and visibility of keys created by Autokey, without needing to pre-plan and create each resource. Using Autokey is simpler than provisioning keys yourself, and is the recommended choice if the keys created by Autokey meet all of your requirements.

Using keys generated by Autokey can help you consistently align with industry standards and recommended practices for data security, including the Multi-tenant Cloud HSM protection level, separation of duties, key rotation, location, and key specificity. Autokey creates keys that follow both general guidelines and guidelines specific to the resource type for Google Cloud services that integrate with Cloud KMS Autokey. After they are created, keys requested using Autokey function identically to other Cloud HSM keys with the same settings.

When you use Autokey, the permissions needed to request a new key are minimal and are included in the default roles that grant resource creation privileges. This means that your developers and infrastructure-as-code (IaC) pipelines don't need elevated privileges. Autokey simplifies using Terraform for key management and supports the principle of least privilege.

You can use Autokey with dedicated-project key storage (formerly known as _centralized key management_) or with same-project key storage (formerly known as _delegated key management_). To use Autokey with dedicated-project key storage, you must have an organization resource that contains a folder resource. When you use dedicated-project key storage, you enable Autokey for projects within a folder, and keys created by Autokey are created in the designated key project for that folder. When you use same-project key storage, you enable Autokey on a folder or project to let Autokey create keys in the same project as the resources that they protect.

For more information about organization and folder resources, see [Resource hierarchy](https://docs.cloud.google.com/resource-manager/docs/cloud-platform-resource-hierarchy).

Cloud KMS Autokey is available in all Google Cloud locations where Cloud HSM is available. For more information about Cloud KMS locations, see [Cloud KMS locations](https://docs.cloud.google.com/kms/docs/locations). There is no additional cost to use Cloud KMS Autokey. Keys created using Autokey are priced the same as any other Cloud HSM keys. For more information about pricing, see [Cloud Key Management Service pricing](https://docs.cloud.google.com/kms/pricing).

## How Autokey works

This section explains how Cloud KMS Autokey works. The following user roles participate in this process:

Administrator
    The administrator is a user who's responsible for managing security at the folder or organization level. An IaC pipeline with elevated permissions can act as the administrator.
Developer
    The application developer is a user who is responsible for creating resources using Cloud KMS Autokey. IaC pipelines can act as the developer.
Cloud KMS administrator
    The Cloud KMS administrator is a user who is responsible for managing Cloud KMS resources. This role has fewer responsibilities when using Autokey than when using manually created keys.

The following service agents also participate in this process:

Cloud KMS service agent
    The service agent for Cloud KMS in a given key project. Autokey depends on this service agent having elevated privileges to create Cloud KMS keys and key rings and to set IAM policy on the keys, granting encrypt and decrypt permissions for each resource service agent.
Resource service agent
    The service agent for a given service in a given resource project. This service agent must have encrypt and decrypt permissions on any Cloud KMS key before it can use that key for CMEK protection on a resource. Autokey creates the resource service agent when needed and grants it the necessary permissions to use the Cloud KMS key.

### Administrator enables Cloud KMS Autokey

To enable Autokey, choose one of the following paths based on your chosen key storage model:

  1. Dedicated-project key storage: Enable dedicated-project key storage on a folder. You designate a dedicated key project to hold the keys that protect resources created in other projects within the folder.
  2. Same-project key storage: Enable same-project key storage on individual projects or for all projects within a folder to create keys in the same project as the resources that they protect.



#### Enable dedicated-project key storage

Before you can use Autokey with dedicated-project key storage in a folder, an administrator must complete the following one-time setup tasks:

  1. Enable Autokey with dedicated-project key storage on the folder and identify the Cloud KMS project that will contain Autokey resources for that folder.

  2. Create the Cloud KMS [service agent](https://docs.cloud.google.com/iam/docs/service-agents) and then grant key creation and assignment privileges to the service agent.




After this configuration is complete, developers who can create Autokey compatible resources in any project in that folder can now trigger Multi-tenant Cloud HSM key creation on-demand. To see full setup instructions for Cloud KMS Autokey, see [Enable Cloud KMS Autokey](https://docs.cloud.google.com/kms/docs/enable-autokey).

#### Enable Autokey with same-project key storage

Before you can use Autokey with same-project key storage, an administrator must complete the following one-time setup tasks:

  1. Enable Autokey with same-project key storage on a project or folder.
  2. Enable the Cloud KMS API on that project or projects in the folder.



When you enable Autokey with same-project key storage on a project, the Cloud KMS [service agent](https://docs.cloud.google.com/iam/docs/service-agents) is created for you when needed. You don't have to manually create the service agent. Any user with permissions to create an Autokey compatible resource can request a new key on demand. To see full setup instructions for Cloud KMS Autokey, see [Enable Cloud KMS Autokey](https://docs.cloud.google.com/kms/docs/enable-autokey).

### Autokey developers use Cloud KMS Autokey

After Autokey is successfully enabled for a project, developers and IaC pipelines can create resources protected using keys created for them on demand. This applies both to projects in a folder where Autokey with dedicated-project key storage is enabled and to projects where Autokey with same-project key storage is enabled. The details of the resource creation process depend on which resource you are creating, but the process follows this flow:

  1. The developer begins to create a resource in a compatible Google Cloud service. During resource creation, the developer requests a new key from the Autokey service agent.

  2. The Autokey service agent receives the developer's request and completes the following steps:

     1. Create a key ring in the project at the selected location, unless that key ring already exists.
     2. Create a key in the key ring with the appropriate granularity for the resource type, unless such a key already exists.
     3. Create the per-project, per-service service account, unless that service account already exists.
     4. Grant the per-project, per-service service account encrypt and decrypt permissions on the key.
     5. Provide the key details to the developer so they can finish creating the resource.
  3. With key details successfully returned by the Autokey service agent, the developer can immediately finish creating the protected resource.




Cloud KMS Autokey creates keys that have the attributes described in the next section. This key creation flow preserves [separation of duties](https://docs.cloud.google.com/kms/docs/separation-of-duties). The Cloud KMS administrator continues to have full visibility and control over keys created by Autokey.

To start using Autokey after enabling it, see [Create protected resources using Cloud KMS Autokey](https://docs.cloud.google.com/kms/docs/create-resource-with-autokey).

## About keys created by Autokey

Keys created by Cloud KMS Autokey have the following attributes:

  * **Protection level:** HSM.
  * **Algorithm:** AES-256 GCM.
  * **Rotation period:** One year.

After a key is created by Autokey, a Cloud KMS administrator can edit the rotation period from the default.

  * **Separation of duties:**
    * The service account for the service is automatically granted encrypt and decrypt permissions on the key.
    * Cloud KMS administrator permissions apply as usual to keys created by Autokey. Cloud KMS administrators can view, update, enable or disable, and destroy keys created by Autokey. Cloud KMS administrators are not given encrypt and decrypt permissions.
    * Autokey developers can only request key creation and assignment. They cannot view or manage keys.
  * **Key specificity or _granularity_ :** Keys created by Autokey have a granularity that varies by resource type. For service-specific details about key granularity, see Compatible services on this page.
  * **Location:** Autokey creates keys in the same location as the resource to be protected.

If you need to create CMEK-protected resources in locations where Cloud HSM is not available, you must create your CMEK manually.

  * **Key version state:** Newly created keys requested using Autokey are created as the primary key version in the enabled state.
  * **Key ring naming:** All keys created by Autokey are created in a key ring called `autokey`. Key rings in your Autokey project are created when an Autokey developer requests the first key in a given location. The `autokey` key ring is created in the designated key project if you're using dedicated-project key storage or in the resource project if you're using same-project key storage.
  * **Key naming:** Keys created by Autokey follow this naming convention: `PROJECT_NUMBER-SERVICE_SHORT_NAME-RESOURCE_TYPE_DESCRIPTOR_NAME-RANDOM_HEX`
  * **Key export:** Like all Cloud KMS keys, keys created by Autokey can't be exported.
  * **Key tracking:** Like all Cloud KMS keys used in CMEK integrated services that are compatible with [key tracking](https://docs.cloud.google.com/kms/docs/view-key-usage), keys created by Autokey are tracked in the Cloud KMS dashboard.



## Controlling Autokey usage

You control how Autokey is used in your organization using the following controls:

  * **Autokey configuration** : You enable Autokey on folders or projects where you want to use it. Autokey configurations are inherited by child resources, but they **can be overridden** by configurations set at a lower level—for example, the Autokey configuration set on a project takes precedence over the configuration of the parent folder. This gives you bottom-up control of Autokey. For more information about enabling and disabling Autokey, see [Enable Cloud KMS Autokey](https://docs.cloud.google.com/kms/docs/enable-autokey).
  * **IAM** : You control who can create and update Autokey configurations and who can create resources protected using Autokey by using IAM role grants and deny policies. These IAM controls can be set at the organization, folder, or project level. IAM role grants let principals perform actions allowed by their role. IAM deny policies block individual permissions, even if they are included in a role granted to the principal. IAM deny policies set on a parent resource **can't be overridden** by more permissive policies set at a lower level; this gives you top-down control over who can enable and use Autokey. For more information about using IAM deny policies to control Autokey use in your organization, see [Use IAM deny policies to control Autokey](https://docs.cloud.google.com/kms/docs/control-autokey-usage#iam).
  * **Organization policy** : You control where and how Autokey can be configured by using custom organization policy constraints. You can enforce organization policy constraints at the organization, folder, or project level. Organization policies are inherited by child resources, but they **can be overridden** by policies enforced at a lower level. For more information about using custom organization policy constraints to control Autokey use in your organization, see [Use custom organization policy constraints to control Autokey ](https://docs.cloud.google.com/kms/docs/control-autokey-usage#cuop).
