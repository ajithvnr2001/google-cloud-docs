#  Deploying Elastic Stack's generative AI features on GDC air-gapped Stay organized with collections  Save and categorize content based on your preferences. 

## Overview

This guide outlines the end-to-end deployment of the Elastic Stack (Elasticsearch and Kibana) on a Google Distributed Cloud (GDC) air-gapped [shared cluster](https://docs.cloud.google.com/distributed-cloud/hosted/docs/latest/gdcag/platform/pa-user/clusters) and demonstrates how to integrate it with a Large Language Model (LLM) service to evaluate Elastic's generative AI features.

The deployment uses the official [Elastic Cloud on Kubernetes (ECK) operator](https://www.elastic.co/guide/en/cloud-on-k8s/current/index.html) available in the GDC air-gapped Marketplace. The operator installs into a project namespace on a shared Kubernetes cluster and automates the provisioning and lifecycle management of Elasticsearch and Kibana resources. Once deployed, Kibana connects to an LLM inference endpoint (such as managed Gemini on GDC or a self-managed OpenAI-compatible service like Ollama or vLLM). This integration powers Elastic's generative AI capabilities, including the [Elastic AI Agent](https://www.elastic.co/docs/explore-analyze/ai-features/agent-builder/builtin-agents-reference#elastic-ai-agent), custom agents built with [Agent Builder](https://www.elastic.co/docs/explore-analyze/ai-features/elastic-agent-builder), and [Attack Discovery](https://www.elastic.co/docs/solutions/security/ai/attack-discovery).

This guide was written for Elastic v9.4.0, the Elastic Kubernetes Operator v3.4.0, and GDC v1.16.2. Some instructions may differ slightly if you are using different versions.

## Architecture

The architecture consists of an Elastic Stack deployment managed by the ECK operator inside a project namespace on a GDC shared user cluster. Kibana communicates over the internal GDC network with an LLM inference endpoint.

![Elastic Stack architecture diagram.](https://docs.cloud.google.com/static/distributed-cloud/hosted/docs/latest/gdcag/solutions/images/elastic-stack-diagram.png)

Key components of this architecture include:

  * **GDC shared cluster** : An organization-scoped [shared Kubernetes cluster](https://docs.cloud.google.com/distributed-cloud/hosted/docs/latest/gdcag/platform/pa-user/clusters) attached to multiple projects, hosting GDC Marketplace software packages and application workloads.
  * **GDC project** : The project namespace on the shared cluster that isolates the ECK operator, Elasticsearch cluster, Kibana instance, and associated Kubernetes Secrets and NetworkPolicies.
  * **Elastic Cloud on Kubernetes (ECK) operator** : Installed from the GDC Marketplace into the project namespace, the operator manages the `Elasticsearch` and `Kibana` custom resources and reconciles the Elastic license required for generative AI features and external LLM connectors.
  * **Elasticsearch** : Stores and indexes operational and security data, and executes search and ES|QL queries generated by Kibana's AI features and agents.
  * **Kibana** : Hosts Elastic's generative AI features, including the Elastic AI Agent (for natural-language log investigation and ES|QL generation), Agent Builder (for building custom conversational agents and tools over Elasticsearch data), and Attack Discovery (for security alert correlation and attack chain analysis). Kibana also manages the LLM action connectors that orchestrate multi-step tool calling between the user, Elasticsearch, and the LLM service.
  * **LLM service** : A managed LLM service (such as Gemini on GDC) or a self-managed inference server (such as Ollama or vLLM) that provides chat completion and tool-calling capabilities to Kibana over the internal GDC network.



## Before you begin

Ensure your GDC environment meets the following prerequisites and assumptions before starting the deployment:

  * **Shared Kubernetes cluster and GDC project** : You have access to an existing GDC [shared cluster](https://docs.cloud.google.com/distributed-cloud/hosted/docs/latest/gdcag/platform/pa-user/clusters) and a GDC [project](https://docs.cloud.google.com/distributed-cloud/hosted/docs/latest/gdcag/platform/pa-user/project-management) attached to that cluster. The project serves as the namespace container for all Kubernetes resources deployed in this guide. Ensure the cluster has sufficient compute and persistent storage resources to host the ECK operator, Elasticsearch, and Kibana workloads.
  * **LLM service** : You have network access to an LLM service, either the managed Gemini service (if available in your GDC environment) or a self-managed OpenAI-compatible LLM service (for example, `gemma4:31b` served via Ollama or vLLM in a GPU project). Deploying the LLM infrastructure itself is out of scope for this guide, but the specific model and API requirements are detailed in Requirements for the LLM service.
  * Retrieve the version of Elastic that comes with your GDC environment:
        
        export ELASTIC_VERSION=$(curl -sk "https://harbor.${ORG}.${ZONE}.${GDCH_DOMAIN}/api/v2.0/projects/library/repositories/elasticsearch%252Felasticsearch/artifacts" | jq -r '[.[].tags[]?.name] | sort_by(split(".") | map(tonumber)) | last')
        

  * Configure environment variables that will be referenced throughout this guide. Modify these values as needed to match your specific environment:
        
        # GDC environment configuration
        export PROJECT_ID="your-project-id"
        export CLUSTER_NAME="your-shared-cluster-name"
        export ZONE="your-zone-name"
        export USER_NAME="your-gdc-user-email"
        
        # Marketplace package and Elastic Stack configuration
        export MARKETPLACE_SERVICE_NAME="elastic"
        
        # LLM service configuration
        export LLM_CONNECTOR_NAME="your-llm-connector-name"
        export LLM_API_URL="http://your-llm-service-host:11434/v1/chat/completions"
        export LLM_MODEL_NAME="your-llm-model-name"
        export LLM_API_KEY="your-llm-api-key"
        

  * Configure `gdcloud`:
        
        gdcloud config set project ${PROJECT_ID}
        gdcloud config set core/zone ${ZONE}
        

  * Request or bind the required project-level IAM roles for your user in the target GDC project (`${PROJECT_ID}`). Based on the [GDC Marketplace lifecycle documentation](https://docs.cloud.google.com/distributed-cloud/hosted/docs/latest/gdcag/application/ao-user/marketplace-lifecycle) and GDC networking requirements, at least the following project roles are required:

    * **Namespace Admin** (`namespace-admin`): Full administrative access to create and manage Kubernetes workloads, Secrets, Services, and custom resources within the project namespace on the shared cluster.
    * **Project Viewer** (`project-viewer`): Read access to view the existing project and its resources in the GDC console and CLI.
    * **Marketplace Editor** (`marketplace-editor`): Permission to install, upgrade, and uninstall GDC Marketplace software packages in the project.
    * **Project NetworkPolicy Admin** (`project-networkpolicy-admin`): Permission to configure global `ProjectNetworkPolicy` rules allowing cross-project and external traffic to reach the Kibana and Elasticsearch LoadBalancer services.

Ask your Organization IAM Admin or Project IAM Admin to grant these roles (or run the following commands if you have IAM administrator privileges):
    
    gdcloud projects add-iam-policy-binding ${PROJECT_ID} \
      --member="user:${USER_NAME}" \
      --role=namespace-admin
    
    gdcloud projects add-iam-policy-binding ${PROJECT_ID} \
      --member="user:${USER_NAME}" \
      --role=project-viewer
    
    gdcloud projects add-iam-policy-binding ${PROJECT_ID} \
      --member="user:${USER_NAME}" \
      --role=marketplace-editor
    
    gdcloud projects add-iam-policy-binding ${PROJECT_ID} \
      --member="user:${USER_NAME}" \
      --role=project-networkpolicy-admin
    

  * Retrieve the kubeconfig for the shared cluster and configure a `ku` shell alias for `kubectl`:
        
        KUBECONFIG=kubeconfig-${CLUSTER_NAME}.yaml gdcloud clusters \
          get-credentials ${CLUSTER_NAME} \
          --zone ${ZONE}
        
        alias ku="kubectl --kubeconfig=kubeconfig-${CLUSTER_NAME}.yaml"

## Deploy the Elastic Stack

### Create the Elastic Stack manifest

The GDC Marketplace package deploys the ECK operator pre-configured to pull Elasticsearch and Kibana container images from the local air-gapped Harbor registry.

Create `elastic-stack.yaml` to deploy a 1-node Elasticsearch cluster, a Kibana UI instance, LoadBalancer HTTP services, and an `allow-all` `NetworkPolicy` in your project namespace (`${PROJECT_ID}`). The manifest also includes a license `Secret` reconciled by the ECK operator, configured here as a 30-day Enterprise trial (`eck-trial-license`) in case you do not have your own Enterprise license yet:
    
    
    cat <<EOF > elastic-stack.yaml
    apiVersion: v1
    kind: Secret
    metadata:
      name: eck-trial-license
      namespace: ${PROJECT_ID}
      labels:
        license.k8s.elastic.co/type: enterprise_trial
      annotations:
        elastic.co/eula: accepted
    ---
    apiVersion: elasticsearch.k8s.elastic.co/v1
    kind: Elasticsearch
    metadata:
      name: elastic-cluster
      namespace: ${PROJECT_ID}
    spec:
      version: ${ELASTIC_VERSION}
      http:
        service:
          spec:
            type: LoadBalancer
      nodeSets:
        - name: default
          count: 1
          config:
            # Disable mmap to avoid requiring privileged host sysctl modifications
            node.store.allow_mmap: false
          podTemplate:
            spec:
              initContainers:
                - name: sysctl
                  securityContext:
                    privileged: false
                    allowPrivilegeEscalation: false
                    runAsNonRoot: true
                    capabilities:
                      drop:
                        - ALL
                  command: ["sh", "-c", "true"]
              containers:
                - name: elasticsearch
                  resources:
                    requests:
                      memory: 2Gi
                      cpu: 500m
                    limits:
                      memory: 4Gi
                      cpu: 2
          volumeClaimTemplates:
            - metadata:
                name: elasticsearch-data
              spec:
                accessModes:
                  - ReadWriteOnce
                resources:
                  requests:
                    storage: 10Gi
    ---
    apiVersion: kibana.k8s.elastic.co/v1
    kind: Kibana
    metadata:
      name: kibana-ui
      namespace: ${PROJECT_ID}
    spec:
      version: ${ELASTIC_VERSION}
      count: 1
      elasticsearchRef:
        name: elastic-cluster
      http:
        service:
          spec:
            type: LoadBalancer
      podTemplate:
        spec:
          containers:
            - name: kibana
              resources:
                requests:
                  memory: 1Gi
                  cpu: 200m
                limits:
                  memory: 2Gi
                  cpu: 1
    ---
    apiVersion: networking.k8s.io/v1
    kind: NetworkPolicy
    metadata:
      name: allow-all
      namespace: ${PROJECT_ID}
    spec:
      podSelector: {}
      policyTypes:
        - Ingress
      ingress:
        - from:
            - ipBlock:
                cidr: 0.0.0.0/0
    EOF

Apply the manifest:

    apiVersion: networking.global.gdc.goog/v1
    kind: ProjectNetworkPolicy
    metadata:
      namespace: ${PROJECT_ID}
      name: allow-inbound-traffic-from-external
    spec:
      policyType: Ingress
      subject:
        subjectType: UserWorkload
      ingress:
        - from:
            - ipBlock:
                cidr: 0.0.0.0/0
    ---
    apiVersion: networking.global.gdc.goog/v1
    kind: ProjectNetworkPolicy
    metadata:
      namespace: ${PROJECT_ID}

      subject:
        subjectType: UserWorkload

## Verify the Elastic license

Elastic's generative AI features (including the Elastic AI Agent, Agent Builder, and Attack Discovery) and external LLM connectors require an Enterprise license (or an active 30-day Enterprise trial license).

When an Elasticsearch cluster is managed by the ECK operator, ECK's `license-controller` continuously reconciles the cluster license against Kubernetes Secrets in the operator namespace (`${PROJECT_ID}`). If you do not yet have a production Enterprise license, the `eck-trial-license` Secret included in `elastic-stack.yaml` (`license.k8s.elastic.co/type: enterprise_trial`) instructs ECK to provision and maintain a 30-day Enterprise trial license automatically. (Note that starting a trial manually via `POST /_license/start_trial` without an ECK license Secret will cause ECK to revert the cluster back to `basic` on the next reconciliation cycle.)

To verify the active license via the CLI:
    
    
    curl -sk -u "elastic:${ELASTIC_PASSWORD}" \
      "https://${ELASTICSEARCH_IP}:9200/_license" | jq .
    

*(Alternatively, in Kibana, open the navigation menu and go to **Management** > **Dev Tools** , then execute `GET /_license` in the Console tab.)*

## Requirements for the LLM service

In a GDC air-gapped environment, cloud-hosted Elastic Managed LLMs and external public SaaS LLM providers are unreachable. Depending on your GDC environment:

  * **Managed Gemini on GDC** : In GDC environments that offer Gemini as a managed LLM service, you can connect Kibana directly to the managed Gemini service if available.
  * **Self-managed LLM service** : Alternatively, you can connect Elastic to a self-managed LLM service hosted within your GDC environment (for example, on GDC GPU nodes).



Deploying a self-managed LLM service is out of scope for this guide. When provisioning or selecting a self-managed LLM service for Elastic, ensure it satisfies the requirements derived from Elastic's official guides:

  * [Configure access to LLMs](https://www.elastic.co/docs/explore-analyze/ai-features/llm-guides/llm-connectors)
  * [Self-managed custom LLMs](https://www.elastic.co/docs/explore-analyze/ai-features/llm-guides/local-llms-overview) (see also [Connect to vLLM in air-gapped environments](https://www.elastic.co/docs/explore-analyze/ai-features/llm-guides/connect-to-vLLM))
  * [LLM and agentic AI observability](https://www.elastic.co/docs/solutions/observability/applications/llm-observability)



### Summary of technical requirements

The following points summarize the key API, model capability, context window, and runtime requirements needed for a self-managed LLM service to work reliably with Elastic's AI Agent, Agent Builder, and Attack Discovery. Note that specific configuration parameter names cited in the following sections (such as `num_ctx`, `num_predict`, `repeat_penalty`, `repeat_last_n`, `OLLAMA_FLASH_ATTENTION`, and `OLLAMA_NUM_PARALLEL`) are provided using Ollama as an example. Apply the equivalent settings if you use another inference engine such as vLLM.

  * **OpenAI-compatible chat completions API (`/v1/chat/completions`) with native function calling**: 
    * Any self-managed inference server (such as Ollama or vLLM) that exposes an OpenAI-compatible `/v1/chat/completions` endpoint (including Server-Sent Events streaming via `"stream": true`) can be integrated using Kibana's OpenAI connector with the provider set to **Other (OpenAI Compatible Service)**.
    * **Enable native function calling** (`"enableNativeFunctionCalling": true`) on the Kibana connector when using models that support cloud native tool calling (such as `gemma4:31b`). By default (`"enableNativeFunctionCalling": false`), Kibana uses prompt-based simulated function calling, which is less reliable during nested tool calls and can fail with parsing errors (such as `Error: Missing name for tool use`). Enabling native function calling delegates tool-call formatting directly to the inference server's OpenAI `tools` protocol.
  * **Instruction-tuned model with native tool and function-calling capabilities** : 
    * Elastic AI Agent (`elastic-ai-agent`) and custom Agent Builder agents rely on multi-step tool calling (`platform.core.list_indices`, `platform.core.get_index_mapping`, `platform.core.search`, `platform.core.execute_esql`, and `platform.core.cases`). They use these tools to discover index mappings, generate and execute ES|QL queries against Elasticsearch, and synthesize findings.
    * The chosen model must be instruction-tuned and capable of generating valid cloud native tool invocations, structured JSON outputs, and ES|QL queries. Refer to Elastic's [LLM performance matrix for Observability](https://www.elastic.co/docs/solutions/observability/ai/llm-performance-matrix) and [LLM performance matrix for Elastic Security](https://www.elastic.co/docs/solutions/security/ai/large-language-model-performance-matrix) for model evaluation criteria.
  * **Context window of at least`128,000` tokens (for example, `num_ctx: 131072` in Ollama)**: 
    * While Elastic's general [self-managed custom LLM documentation](https://www.elastic.co/docs/explore-analyze/ai-features/llm-guides/local-llms-overview) cites a 64,000-token minimum, a **128,000-token context window (`131,072` tokens)** is strongly recommended for Elastic AI Agent (`elastic-ai-agent`).
    * During multi-step investigations, the agent combines system instructions and tool definitions with index schemas, ES|QL documentation, and raw search results (for example, retrieving up to 100 sample documents to inspect field values before aggregating). A single investigation can exceed 70,000 tokens in conversation history, which causes a 64,000-token context window to truncate the prompt mid-conversation.
    * Note that in Ollama, a `PARAMETER num_ctx` directive baked into a model's `Modelfile` overrides the container's `OLLAMA_CONTEXT_LENGTH` environment variable. Ensure both `OLLAMA_CONTEXT_LENGTH=131072` and `PARAMETER num_ctx 131072` in the model's `Modelfile` are configured (on an 80 GB NVIDIA A100 or H100 GPU, `gemma4:31b` at `128K` context fits comfortably in VRAM).
  * **Output token limit and gentle repetition penalty (for example,`num_predict: 8192` and `repeat_penalty: 1.05` in Ollama)**: 
    * Kibana's OpenAI stream adapter treats `"finish_reason": "length"` as a fatal `Token limit reached` error and sends `"temperature": 0` (greedy decoding) in every request.
    * For reasoning-capable models (such as `gemma4:31b`, which generates internal thought tokens before emitting tool calls), configure an output token limit of at least `8,192` tokens and a gentle repetition penalty. For example, in Ollama, set `num_predict: 8192`, `repeat_penalty: 1.05`, and `repeat_last_n: 64`. Avoid overly aggressive repetition penalties (such as `1.15+` over large windows), as they penalize the model when copying an ES|QL query from its internal reasoning block into the final tool-call JSON.
  * **GPU acceleration, Flash Attention, and parallel KV cache slots ( <60s per turn)**: 
    * Kibana's OpenAI connector enforces a default 60-second HTTP timeout per streaming turn.
    * Because a single agent turn can trigger nested LLM sub-calls (for example, to translate natural-language search requests into ES|QL queries while the main agent conversation is active), running an inference server with only a single KV cache slot can cause sub-calls to evict the main conversation's cached context and slow down subsequent turns.
    * In Ollama, set `OLLAMA_FLASH_ATTENTION=1` and `OLLAMA_NUM_PARALLEL=2` so that Flash Attention accelerates long-context evaluation and the main conversation and nested sub-calls maintain separate KV cache slots in GPU memory.

### Attack Discovery

[Attack Discovery](https://www.elastic.co/docs/solutions/security/ai/attack-discovery) is an AI feature in Elastic Security that analyzes open security alerts, maps them to the MITRE ATT&CK framework, and correlates related alerts, IP addresses, and user accounts into visual attack chains. Because Attack Discovery requires a large model to synthesize multi-alert structured JSON outputs reliably, use a 30B-class or larger model (such as `gemma4:31b`).

#### Generate security alerts from the sample logs

By default, the `kibana_sample_data_logs` dataset contains raw web access logs and does not populate the Elastic Security alerts index (`.alerts-security.alerts-default`). In addition, Kibana's sample data generator assigns future `@timestamp` values (up to 30 days ahead) to the 100 scanning and exploitation requests from `30.156.16.164`, which places them outside the `now-30d` to `now` window queried by Elastic Security detection rules.

To demonstrate Attack Discovery with the sample logs, shift the `@timestamp` of `30.156.16.164`'s records back by 30 days, enrich them with Elastic Common Schema (ECS) `source.ip` and `user.name` fields, and create two detection rules that generate security alerts from those events:

  1. Map `clientip` to `source.ip`, set `user.name` (`www-data`), and shift `@timestamp` back 30 days on the `30.156.16.164` records in `kibana_sample_data_logs*`:
         
         curl -sk -u "elastic:${ELASTIC_PASSWORD}" \
           -X POST "https://${ELASTICSEARCH_IP}:9200/kibana_sample_data_logs*/_update_by_query?conflicts=proceed&refresh=true" \
           -H "Content-Type: application/json" \
           -d '{
             "query": {
               "term": {
                 "clientip": "30.156.16.164"
               }
             },
             "script": {
               "source": "ctx._source.source = [\"ip\": ctx._source.clientip]; ctx._source.user = [\"name\": \"www-data\"]; ctx._source[\"@timestamp\"] = ZonedDateTime.parse(ctx._source[\"@timestamp\"]).minusDays(30).toString();",
               "lang": "painless"
             }
           }' | jq '{updated: .updated, failures: .failures}'
         

  2. Create two Elastic Security detection rules targeting `kibana_sample_data_logs*`. The first rule detects Nmap and WordPress login probing (`Reconnaissance`), and the second rule detects `/etc/passwd` path traversal and remote command execution attempts (`Initial Access`):
         
         curl -sk -u "elastic:${ELASTIC_PASSWORD}" \
           -X POST "https://${KIBANA_IP}:5601/api/detection_engine/rules" \
           -H "kbn-xsrf: true" \
           -H "Content-Type: application/json" \
           -d '{
             "name": "Suspicious Web Reconnaissance and Vulnerability Scanning",
             "description": "Detects Nmap active scanning and WordPress login/plugin probing in web access logs.",
             "risk_score": 47,
             "severity": "medium",
             "type": "query",
             "language": "kuery",
             "query": "clientip: \"30.156.16.164\" and (request: *nmap* or request: *wp-login*)",
             "index": ["kibana_sample_data_logs*"],
             "from": "now-30d",
             "interval": "1h",
             "max_signals": 2,
             "enabled": true,
             "threat": [
               {
                 "framework": "MITRE ATT&CK",
                 "tactic": {
                   "id": "TA0043",
                   "name": "Reconnaissance",
                   "reference": "https://attack.mitre.org/tactics/TA0043/"
                 },
                 "technique": [
                   {
                     "id": "T1595",
                     "name": "Active Scanning",
                     "reference": "https://attack.mitre.org/techniques/T1595/"
                   }
                 ]
               }
             ]
           }' | jq '{id: .id, name: .name, enabled: .enabled}'
         
         curl -sk -u "elastic:${ELASTIC_PASSWORD}" \
           -X POST "https://${KIBANA_IP}:5601/api/detection_engine/rules" \
           -H "kbn-xsrf: true" \
           -H "Content-Type: application/json" \
           -d '{
             "name": "Web Path Traversal and Remote Command Execution Attempt",
             "description": "Detects path traversal attempts targeting /etc/passwd and Cisco IOS privilege level 15 remote command execution (/level/15/exec).",
             "risk_score": 73,
             "severity": "high",
             "type": "query",
             "language": "kuery",
             "query": "clientip: \"30.156.16.164\" and (request: *passwd* or request: *exec*)",
             "index": ["kibana_sample_data_logs*"],
             "from": "now-30d",
             "interval": "1h",
             "max_signals": 2,
             "enabled": true,
             "threat": [
               {
                 "framework": "MITRE ATT&CK",
                 "tactic": {
                   "id": "TA0001",
                   "name": "Initial Access",
                   "reference": "https://attack.mitre.org/tactics/TA0001/"
                 },
                 "technique": [
                   {
                     "id": "T1190",
                     "name": "Exploit Public-Facing Application",
                     "reference": "https://attack.mitre.org/techniques/T1190/"
                   }
                 ]
               }
             ]
           }' | jq '{id: .id, name: .name, enabled: .enabled}'
         

  3. Wait approximately 60 seconds for the initial rule execution to complete, then verify that 4 alerts have been indexed into `.alerts-security.alerts-default`:

           "https://${ELASTICSEARCH_IP}:9200/.alerts-security.alerts-default/_search?size=4" \
           | jq '.hits.hits[]._source | {rule: .["kibana.alert.rule.name"], source_ip: .source.ip, user_name: .user.name, request: .request}'
